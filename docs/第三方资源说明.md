# 第三方资源说明

本文件说明 RightKit 仓库里**哪些资源属于第三方**、为什么这样处理，以及新增资源时该遵守什么规则。

> 这是工程约定，不是法律意见。涉及正式分发时请自行咨询律师。

## 一、先分清两件事

商标和版权是**两套独立的法律**，处理方式不同：

| | 管什么 | 触发条件 | 例子 |
| --- | --- | --- | --- |
| **版权** | 具体的作品文件 | **复制文件**即可能侵权 | 把 VS Code 的 `icon.png` 提交进仓库 |
| **商标** | 品牌与来源识别 | 让用户误以为有官方关联、或拿它当自己的品牌 | 把 App 命名为 "VS Code Helper" |

**关键结论：只要不把文件放进仓库，版权这一半基本就规避了。** 商标那一半靠「正当指示性使用」——用某个图标只是为了指明"这个功能会调用那个软件"，属于常见且被普遍接受的做法。

## 二、本仓库的规则

1. **绝不提交第三方的图标 / 图片文件。** 包括但不限于 VS Code、Python、Keka、终端等。
2. **品牌图标一律在运行时从用户已安装的应用里取。** 脚本包只存 `applicationBundleIdentifier`，运行期用 `NSWorkspace` 解析；用户本机本来就有那个应用，图标是**他自己的副本**。
3. **取不到就回退到自己画的符号**（SF Symbols），不引入任何替代性的山寨图标。
4. **用户可以自己放图标。** 脚本包内放 `icon.png` 即生效，风险由放的人承担。
5. **GPL 的连带问题**：本仓库以 GPL-3.0 分发。把他人图标放进来，等于**声称你有权以 GPL 授权它**——而你并没有。这比"用了别人的图"更麻烦，因为它会误导下游使用者。

## 三、机械保障（不靠自觉）

| 手段 | 位置 | 拦住什么 |
| --- | --- | --- |
| `.gitignore` | 仓库根 | 内置脚本目录下生成的 `icon.png` 被误提交 |
| 单元测试 | `Tests/BuiltinScriptAssetsTests.swift` | 内置脚本未声明 `icon`、或**仓库内出现 `icon.png`** |
| 单元测试 | 同上 | 声明的 `applicationBundleIdentifier` 在本机解析不到 |

## 三之二、用户机器上生成的 icon.png 算不算侵权？

**不算分发，因此不构成这批规则要防的问题。**

| | 谁复制 | 是否分发 |
| --- | --- | --- |
| 图标进仓库 | 项目作者 | ❌ 是——每个 clone / 构建的人都在下载他人作品 |
| 图标进脚本文件夹 | **用户的 Mac**，从**用户自己已安装的应用**里读取 | ✅ 不是——本地副本，自用 |

判断依据：**是用户自己的机器、从用户已获授权的副本里、为用户自己在屏幕上显示而生成的本地副本。**
macOS 自身在 Finder、Dock、⌘Tab 里到处渲染这个图标，所有启动器、窗口切换器、截图工具也都是这么做的。
项目分发出去的只是**读取图标的代码**，不是图标本身。

### 唯一的传播路径

脚本包是设计成**可以分享**的。把整个 `Open in VS Code/` 文件夹打包发给别人时，`icon.png` 会跟着走——**那一步才是分发**。

处理办法很简单：

1. **分享前删掉 `icon.png`。** App **每次启动都会检查并补齐**缺失的图标，所以对方拿到后会在他自己机器上重新生成一个。
2. **图标自带溯源信息。** 生成的 PNG 里写入了 XMP `dc:description`：

   ```
   Generated locally by RightKit from com.microsoft.VSCode.
   Do not redistribute; delete this file before sharing the script package.
   ```

   即使文件被转走，用任何图片工具都能看到它的来源与注意事项。

3. **也可以完全不要这个文件。** 删掉后不重启，界面会自动回退到运行期解析出的应用图标；把内置脚本 `config.json` 里的
   `"icon": "icon.png"` 去掉，则彻底回到「不落盘、每次运行期解析」的模式。

## 三之三、唯一的例外：Python 语言 logo

`Resources/BuiltinScripts/Run Python/icon.png` **是随仓库分发的**，与应用图标（VS Code / Keka / 终端）的处理方式相反。

**为什么破例**

- 它标志的是**语言**，不是某个第三方应用：图标的含义是"这个脚本跑的是 Python"，
  属于最典型的**指示性使用**。应用图标则是另一个应用的品牌，含义和使用场景都不同。
- **没有可靠的本地来源。** 实测本机三种可能来源都不是干净的 logo：
  - `/Applications/Python*/IDLE.app` → "文稿 + logo + 钢笔"的合成图
  - `Python.framework/.../Python.app`（`com.apple.python3`）→ 火箭 + logo
  - `.py` 的文件类型图标 → 普通文稿（因为默认打开程序不是 Python 专属）
  
  唯一干净的副本在 VS Code 的 Python 扩展里（`~/.vscode/extensions/ms-python.python-*/icon.png`）。
  依赖编辑器扩展来给"运行 Python 脚本"取图标，既脆弱又讲不通。
- **代价可控**：这是一次一文件替换。若权利方有异议，删掉 `icon.png` 并去掉
  `config.json` 里的 `"icon"`，App 会在本机按 `applicationBundleIdentifier` 重新生成一个。

**约束**：单元测试 `testOnlyThePythonLogoShipsAnIcon` 钉住了这条规则——**除
`Run Python` 之外的任何内置脚本包，一旦出现 `icon.png` 就会测试失败**，
以防将来有人把本机生成的应用图标误提交进来。

## 五、已知待处理项：Office 起始文档

`Empty.docx` 与 `Empty.pptx` 由 `python-docx` / `python-pptx` 生成，而这两个库自带的默认模板**源自真实的 Word / PowerPoint 文档**。证据在文件的元数据里：

```
Empty.docx  docProps/app.xml: <Application>Microsoft Macintosh Word</Application>
                              <Template>Normal.dotm</Template>
Empty.pptx  docProps/app.xml: <Application>Microsoft Macintosh PowerPoint</Application>
                              <cp:lastModifiedBy>Steve Canny</cp:lastModifiedBy>   # python-pptx 作者
Empty.xlsx  docProps/app.xml: <Application>Microsoft Excel Compatible / Openpyxl 3.1.5</Application>
```

后果是这两个文件里带着大量 Word / PowerPoint 生成的 XML：`Empty.docx` 解压后 826KB，其中 `word/styles.xml` 349KB、`word/stylesWithEffects.xml` 438KB。

**实际风险偏低**：OOXML 是 ECMA-376 国际标准，这些内容多为功能性定义（样式表、主题色值、字体名），且 python-docx / python-pptx 以 MIT 分发这些模板，海量项目都在无意中分发同样的字节。

**若要彻底干净**，做法是自己拼最小 OOXML（`[Content_Types].xml` + `_rels/.rels` + `word/document.xml`）。`styles.xml` 与主题都是**可选**的，去掉后 Word / Pages / LibreOffice 仍能正常打开，文件会从 36KB 降到约 2KB。

## 六、新增内置脚本时的清单

- [ ] 脚本包内**不放**图标文件，改为在 `config.json` 声明 `applicationBundleIdentifier`
- [ ] `config.json` 同时声明 `"icon": "icon.png"`（App 会在用户本机据此生成）
- [ ] 显示名用中文
- [ ] 跑 `xcodebuild test`，资源测试会校验以上各点
