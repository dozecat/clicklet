# RightKit 项目结构

本文档说明工程目录、target 职责与分层规则。

## 一、架构总览

三个进程 target，通过 App Group、URL Scheme 和 XPC 明确分工：

```
FinderSyncExtension                RightKit.app                 ScriptXPCService
（右键菜单、轻量动作）    →      （交互、编排、设置界面）    →     （脚本执行）
          |                              |
          └──── App Group 请求/快照 ─────┘
```

- Finder 扩展不直接连接 `ScriptXPCService`。主 App 内嵌的 XPC Service 只对主 App 可见。
- 扩展把操作写入 App Group 的请求队列，再打开 `rightkit://action/<UUID>` 唤起主 App。
- 主 App 负责所有用户交互、脚本目录扫描、压缩器编排和通知。
- 脚本任务由主 App 通过 `NSXPCConnection` 发往 `ScriptXPCService`。
- `Shared/` 只放跨进程模型、存储和 IPC；`AppCore/` 只编入主 App 与测试。

## 三、target 与 Bundle Identifier

| Target | 类型 | Bundle Identifier | 职责 |
| --- | --- | --- | --- |
| `RightKit` | Application | `com.dozecat.RightKit` | 设置窗口、操作协调、模板/脚本/压缩配置、通知 |
| `FinderExtension` | Finder Sync Extension | `com.dozecat.RightKit.FinderExtension` | 沙盒内构建菜单、复制路径、发送请求 |
| `ScriptXPCService` | XPC Service | `com.dozecat.RightKit.ScriptXPCService` | 仅接受主 App 调用，隔离执行用户脚本 |
| `RightKitTests` | Unit Test Bundle | `com.dozecat.RightKitTests` | 共享业务逻辑单元测试 |

`FinderExtension` 与 `ScriptXPCService` 由 `RightKit.app` 内嵌。

## 四、分层规则

| 层 | 位置 | 规则 |
| --- | --- | --- |
| Finder 扩展 | `FinderExtension/` | 只构建菜单、处理无需主 App 的动作（拷贝路径/文件名、开终端）、序列化其余请求 |
| Action Coordinator | `RightKit/Services/ActionCoordinator.swift` | 接收入口，展示交互并编排后续任务 |
| App 业务 | `AppCore/` | 扫描脚本、创建文件、压缩编排，不 import SwiftUI |
| Model | `Shared/Models.swift` | Codable 数据结构，无逻辑 |
| Storage / IPC | `Shared/Storage.swift`、`Shared/ActionProtocol.swift`、`Shared/IPC.swift` | App Group、请求模型、XPC 协议与常量 |

判断标准：

- 三个进程都需要的数据与协议 → `Shared/`
- 只有主 App 需要的业务 → `AppCore/`
- 平台交互与界面 → `RightKit/`
- `FinderExtension` 不包含文件写入、脚本扫描或压缩器实现

## 五、数据与通信

- App Group：`$(TeamIdentifierPrefix)group.com.dozecat.RightKit`。
- **用户设置**（启用开关、排序、压缩软件选择）：App Group 容器 `State/preferences.json`，通常只有 1KB 左右。注意这里**只有偏好**，脚本正文与图标在下一节的脚本目录里——两者分开，因此单导出这份 JSON 并不是可用的备份。
- **主 App 是被唤起的，不是被请到前台的**：扩展打开 `rightkit://` 时把 `OpenConfiguration.activates` 设为 `false`。若让 App 抢到前台，它会与 Finder 争抢焦点（就地重命名因此失败），并且每次动作都会让已打开的设置窗口闪一下。App 仍在后台正常启动并处理 URL——`activates` 只控制激活，不控制是否启动。
- **关闭窗口状态恢复**：`applicationShouldSaveApplicationState` / `applicationShouldRestoreApplicationState` 返回 `false`。macOS 默认会重开上次退出时开着的窗口，对一个被右键动作唤起的工具来说，表现为「新建文件自己把设置窗口叫了出来」。用应用级开关而不是 SwiftUI 的 `.restorationBehavior`——后者需要 macOS 15，而 `SceneBuilder` 无法表达可用性判断。
- 设置窗口用 SwiftUI 的 `Settings` 场景而非 `Window`：后者**启动即开窗**，于是每个经 URL 唤起的右键动作都会先闪一下设置窗口。`Settings` 场景启动时**不创建窗口**（探针实测 `NSApp.windows.count == 0`），打开它只有一个受支持的入口：`SettingsLink` / `openSettings`（均为 macOS 14+）。
- **不要用 `showSettingsWindow:` selector 打开设置窗口**：macOS 14 起它**返回 `true` 却什么都不做**，看起来成功、请求被静默丢弃（探针实测：`sendAction -> true, windows=0`）。`SettingsOpener` 因此改为**执行应用菜单里的「设置…」项**（`SettingsLink` 会在那里装一个 `menuAction:`，`performActionForItem` 可编程触发，探针实测 `windows=1 visible=1`），菜单项按 ⌘, 或标题定位，不依赖界面语言。
- 菜单快照与扩展请求：App Group 容器 `State/menu-snapshot.json`、`Requests/`（均为派生数据，不必备份）。快照里含菜单图标（16pt PNG 的 base64），因为沙盒中的扩展无法自行解析应用与文稿图标。
- 用户模板：App Group 容器 `Templates/`。
- 用户脚本：`~/Library/Application Support/RightKit/Scripts/`；内置脚本首次启动时播种到这里，已播种的名字与内容指纹记在 `~/Library/Application Support/RightKit/seeded-scripts.json`（指纹用于判断副本是否被用户改过，决定能否安全升级）。
- 脚本执行日志：`~/Library/Logs/RightKit/`。
- 诊断日志：App Group 容器 `Logs/rightkit.log`（主 App 与扩展共同追加）。
  扩展在自己的进程里运行，它的 `NSLog` 正文在统一日志里是 `<private>` 脱敏的，
  因此排查"右键菜单不生效"必须依赖这个文件；不要直接读统一日志。
- 脚本执行：Finder 扩展 → 主 App → `ScriptXPCService`。
- 脚本源目录是事实源；主 App 扫描并写入菜单快照，扩展只读快照。

### 一次右键的完整链路

**① 轻量动作（拷贝路径、拷贝文件名、在终端中打开）** —— 全程留在扩展里，不唤起主 App：

```
右键 → 扩展读快照构建菜单 → 用户点击 → 扩展直接写剪贴板 / 请 LaunchServices 开终端
```

**② 需要主 App 的动作（新建文件、压缩、解压）** —— 扩展没有权限跑外部进程，只能转交：

```
右键 → 扩展读快照 → 用户点击
     → 扩展写 Requests/<uuid>.json，再 open rightkit://action/<uuid>
     → 主 App 的 onOpenURL / application(_:open:) 收到
     → ActionCoordinator 取出并删除请求，按 kind 分发
     → NewFileService 建文件 / ArchiveService 跑命令 → 通知 + 在 Finder 中选中
```

关键约束：**`NSMenuItem.representedObject` 跨 XPC 边界一定会丢**（不论什么类型）。
所以菜单项只用「独立 selector + 标题/tag」传递身份，由 `MenuCommandRegistry` 还原 ID。

**③ 脚本** —— 比 ② 多一跳，落到 XPC 服务里执行：

```
扩展 → 主 App（校验快照，解析脚本路径）
     → NSXPCConnection → ScriptXPCService → 执行 script.sh
     → 结果回到主 App → 通知
```

脚本带 300 秒超时；stdout/stderr 写 `~/Library/Logs/RightKit/Scripts/<脚本名>/`；
XPC 服务继承的是 launchd 最小环境（`/usr/bin:/bin:/usr/sbin:/sbin`），
所以脚本要自己补 PATH，否则 `/opt/homebrew/bin` 下的 python3/node 找不到。

## 六、XcodeGen 使用方法

工程文件 `RightKit.xcodeproj` 由 `project.yml` 生成，**不入库**。

```sh
# 首次安装
brew install xcodegen

# 生成 / 重新生成工程
xcodegen generate

# 打开
open RightKit.xcodeproj
```

以下情况需要重新执行 `xcodegen generate`：

- 修改了 `project.yml`
- 新增 / 删除 / 移动了源文件

## 七、改完扩展必须重载

Finder 把 Finder Sync 扩展加载在**自己的进程**里并长期持有。重新编译只会替换磁盘上的二进制，**已经在跑的进程仍然执行旧代码**，表现为"改了没生效 / bug 修复了却还是坏的"。

每次改完 `FinderExtension/` 后执行：

```sh
Scripts/reload-finder-extension.sh
```

等价于手工执行：

```sh
pkill -x FinderExtension                                        # 结束旧进程，Finder 下次右键时重新拉起
pluginkit -e use -i com.dozecat.RightKit.FinderExtension        # 确认扩展处于启用状态
killall Finder                                                  # 保险起见让 Finder 重新加载（会关掉所有 Finder 窗口）
```

也可以在「通用」设置页拨一下「访达拓展」开关，效果相同且不会关闭 Finder 窗口。

排查时同时盯住诊断日志（主 App 与扩展共同写入）：

```sh
tail -f ~/Library/Group\ Containers/*group.com.dozecat.RightKit/Logs/rightkit.log
```
